Section 01 · The mental model

Two systems, working together.

Think of CLAUDE.md as your SDR's onboarding doc. It's the same every morning. The actual conversation? That's the call — different every time. One is deterministic. One is probabilistic. The system works when both are clean.

Deterministic

Files, commands, hooks.

Always do the same thing. Settings.json, CLAUDE.md, skills, slash commands. You write them once, they fire predictably forever. This is the surface you control.

Probabilistic

Claude's reasoning.

Same input, different output. The model thinks fresh every turn. You can shape it with context (CLAUDE.md, memory, skills) — but you can't make it deterministic. Stop trying.

03/11
Section 02 · The file types

Three file types do most of the work.

Open any production .claude folder and you'll see the same three extensions over and over. Each does one job.

.md

Markdown

The instructions Claude reads. CLAUDE.md, SKILL.md, rules, memory entries — all written in plain markdown. Human-readable, version-controllable, no syntax to learn.

CLAUDE.md · SKILL.md · MEMORY.md
.json

JSON config

The settings the harness reads. Permissions, hooks, environment defaults. Strict syntax — one missing comma breaks it. Lives at .claude/settings.json.

settings.json · .mcp.json
.ts / .py

Code (when you need it)

For pipelines that actually run — Trigger.dev tasks, scripts, helpers. Skills can call into these. Claude doesn't read them as instructions; it executes them.

tasks/*.ts · scripts/*.ts

Section 03 · A prompt's journey

What happens when you type a prompt.

The .claude/ folder isn't a thing you read top-to-bottom. It's a set of files Claude reaches for at different moments while it works. Follow a single prompt left-to-right — then we'll go deep on each stage.

01 · TYPE

You give Claude a task.

Where it starts. Just plain text in the terminal — same as ChatGPT, but inside your project folder.
Your prompt "Draft three cold emails for this prospect."
02 · BRIEF

Claude reads its standing brief.

Loaded automatically every single prompt — like the briefing your SDR re-reads every morning.
CLAUDE.md Project context — who you serve, what's on, where the source docs live.
memory/MEMORY.md A notebook of things you've taught Claude in past sessions.
03 · DECODE

Claude figures out what you mean.

If you typed a /slash, it loads the matching workflow. Otherwise it interprets the prompt directly.
.claude/skills/ Saved workflows you trigger with /skillname — like /gtm-snapshot.
.claude/commands/ One-keystroke shortcuts for runs you do over and over.
04 · WORK

Claude does the task.

As Claude touches files, it pulls in the rulebooks and source-of-truth docs that apply.
.claude/rules/ House rules. Auto-load when you're editing certain files (e.g. banned phrases when writing copy).
.claude/os/ The source of truth — ICP, tone, current offer. Pulled in only when needed.
05 · ACT

Things actually run.

Before any command fires, the harness checks what's allowed. Hooks auto-fire on certain events.
.claude/settings.json The permission slip. What can run without asking — plus hooks that fire automatically.
↩ memory updates If Claude learned something worth keeping, it writes a new note for next time.

Stage 02 · Brief — the standing context

CLAUDE.md is an index, not a dump.

Every prompt loads CLAUDE.md into context. If it's 8,000 words of strategy, every conversation pays that token cost. Treat it like a homepage — point to the deep docs, don't paste them in.

# Acme Outbound — Project Context ## Outbound OS Source-of-truth copy lives in .claude/os/: - .claude/os/ICP.md — targeting + scoring - .claude/os/TOV.md — tone of voice, banned phrases - .claude/os/BRIEFING.md — current offer + locked CTAs Copy loading rules → .claude/rules/outbound-copy.md ↑ auto-loads when working in .claude/os/ or outbound-engine/

Each line is a pointer. Claude only loads the deep doc when the work demands it — not on every "hi."

Stage 02 · Brief — persistent notes

Memory is an index. Same as CLAUDE.md.

MEMORY.md loads into every prompt. Each entry is one line — pointer + hook. The full memory body lives in its own file and only loads when relevant.

Stage 03 · Decode → 04 · Work

Skills can nest and reference.

A skill is a saved workflow you trigger with /skillname. The SKILL.md file holds the instructions — and as it runs, it pulls in rules, source-of-truth docs, and even other skills (this is where Stage 04 · Work happens).

/skill /cold-email Top-level entry point — write a sequence for one prospect.
loads → .claude/os/TOV.md + BRIEFING.md Source-of-truth docs referenced inside SKILL.md.
loads → .claude/rules/outbound-copy.md Auto-loaded by glob — banned phrases, template scoring.
calls → /gtm-snapshot Nested skill invocation — pulls fresh ICP fit before drafting.

The pattern: one skill, many references. Keep each skill narrow; let it pull what it needs.

08/11
Stage 03 · Decode — alternate entry points

Two more ways to start a run.

Slash commands

.claude/commands/*.md

A markdown file with a description. Triggered by /filename. Use for repeatable runs you want one-keystroke access to — pipelines, checks, daily reviews.

Subagents

.claude/agents/*.md

A focused worker with its own tools and posture. Use for orchestration jobs Claude shouldn't drift on — campaign runs, code reviews, deployments.

And /loops — Claude runs a prompt on an interval. Great for monitoring pipelines while you focus elsewhere. We go deep on these next lesson.

Stage 05 · Act — the harness

settings.json — permissions + hooks.

Two jobs. Permissions tell the harness which commands run without asking. Hooks are shell commands that always fire on certain events. The harness executes both — Claude doesn't.

{ "permissions": { "allow": [ "Bash(curl -s https://api.notion.com/*)", "Bash(firecrawl scrape *)", "mcp__claude_ai_Notion__notion-fetch" ] }, "hooks": { "UserPromptSubmit": [{ "hooks": [{ "type": "command", "command": "echo prompt logged >> ~/.claude/log" }] }] } }

Bonus · Version control

GitHub, in three commands.

GitHub is where your .claude/ folder lives between machines. A repo is a folder with history. Three commands cover 90% of what you need.

git pull
Get the latest
Sync the remote's changes down to your machine. Run before you start working — avoids conflicts later.
git commit -m "..."
Save a snapshot
Bundles your changes with a message. Stays local until you push. Commit early, commit often, write real messages.
git push
Send it up
Pushes your commits to GitHub. Now your laptop, your server, and your teammate all see the same .claude/ folder.

Rule of thumb: never commit .env. Always commit .claude/.
